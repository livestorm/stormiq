# Backend

The HTTP routes live in `routes/`, one module per area; `../app.py` creates the app and includes their routers in order, with the SPA catch-all (`routes/spa.py`) last. Route handlers are plain `def` functions, run in FastAPI's threadpool. Module map: [docs/architecture.md](../docs/architecture.md#backend-code).

## Rules

**Access**
- A new route goes in the router module for its area (`routes/`), never on `app` directly; request bodies go in `routes/models.py`.
- Routes take their identity from `auth.py`: `Depends(get_caller)`, `Depends(require_admin)` or `Depends(get_optional_caller)`. Never read the session cookie or resolve org ids by hand.
- Session reads pass the caller's scope (`organization_id=caller.read_scope`). Only admin, local-dev and worker code pass `ALL_ORGS`. A blank scope matches nothing, and an out-of-scope session looks missing (404).
- Stamp `organization_id` on a row only after the caller's own Livestorm credentials returned the session. → [docs/security.md](../docs/security.md)

**Database (`db.py`)**
- All SQL lives in `db.py` and goes through the pooled `get_db_connection()`. Pass values as query parameters, never by string formatting.
- Schema changes go in `ensure_database_schema()` and must be idempotent (`IF NOT EXISTS`); there is no migration tool.
- Write an AI bundle with `merge_cached_bundle_entry` (one language or tone), never by rewriting the whole bundle, and pass `provenance=ai.usage.run_provenance()`: the same write keeps the version in `output_versions`. Writes raise on failure; don't swallow them.
- One narrow exception, decided by the owner: a failed `insert_llm_usage` doesn't fail the AI job. `ai.usage.record_call` logs the row as a line at ERROR (no content, no secrets) and the job saves its output, which is complete and paid for. Don't extend this to any other write. → [docs/data-model.md](../docs/data-model.md#caching-rules)
- Hot paths (polls, job starts, the v1 record) read with `fetch_session_fields`; add a field to `_SESSION_FIELD_SQL` rather than loading the full row. → [docs/data-model.md](../docs/data-model.md)
- A session's people are written only by `replace_session_roster`, whole, in one transaction: `parse_person` rows plus a `P-` ref, never an email address or a join link. They are read only through `fetch_roster_status` and `list_session_people`, which join `session_cache` for the org scope, and `fetch_session_roster`, which calls both and returns a header and its rows of one roster version (use it whenever you need the people with their header: the two reads alone can straddle a sync). A sync row's connection id is handed over once, by `claim_livestorm_sync`; never return or log it. A row that is never claimed is closed through `update_livestorm_sync` (a failed enqueue, a lost job found by a status read) or `sweep_stuck_livestorm_syncs`, which clear it. `replace_session_roster` has no default for `refresh_due_at`: pass the stored value to keep a due refresh. → [docs/data-model.md](../docs/data-model.md#stored-people)

**Jobs (`queue.py`, `worker.py`)**
- Enqueue only through `queue.enqueue_unique_job_sync`, with a deterministic id (`ai_job_id`, `transcription_job_id`, `cover_image_job_id`, `surprise_voice_job_id`, `livestorm_sync_job_id`).
- Job arguments are ids only: no keys, tokens or connection ids.
- A handler that users watch publishes progress (`progress.publish_progress_sync`) and clears it in `finally`. Every handler re-raises failures so arq records them (marking its own Postgres row `error` first, if it has one, as transcription and the people sync do) and is registered in `WorkerSettings.functions` with its own `timeout`. arq stores only a failed job's message (`queue.job_result_serializer`), which the poll shows: keep keys, tokens and upstream bodies out of it, and keep `WorkerSettings.job_serializer` set. The people sync raises its own `people_sync.PeopleSyncFailed`. → [docs/jobs.md](../docs/jobs.md)

**Outbound calls**
- Every HTTP call has a timeout. Retry only failures where nothing was produced or billed; never retry a POST that starts paid work. → [docs/providers.md](../docs/providers.md)
- Anthropic is called only through the SDK client `llm_client._anthropic_client` (one per process, the key and host passed explicitly, `max_retries=0`) inside `_with_transport_retry`. Never build another client, turn the SDK's retries on, or retry a timeout (catch `APITimeoutError` before `APIConnectionError`, its parent) or a stream after its first event. A failed call raises `LLMProviderError`, never the SDK's own error, which arq can't store. Keep the `anthropic` pin below 2 while a classic output sends `temperature`. → [docs/providers.md](../docs/providers.md#the-anthropic-sdk)
- The Livestorm HTTP session (`livestorm.client.livestorm_get`) is shared by all users: no cookies, no per-user state.
- A job that calls Livestorm with a user's connection resolves it in the worker, after checking that the connection's org is the session's stamped org (`people_sync._resolve_sync_credentials`); on a mismatch it makes no call. Only a member of the session's org starts a people sync (`people_sync.start_people_sync`), and its guards (cooldown, error backoff, the per-org daily call cap `LIVESTORM_SYNC_DAILY_CALLS_PER_ORG`, checked on the web side and again in the worker, one sync per org at a time with one more waiting at most) stay in front of every new way to start one. A fetch starts one too (`people_sync.start_sync_on_fetch`, as an automatic start), best-effort: `api_logic._roster_sync_on_fetch` never lets a failed start fail the fetch, and logs the error's class, never its message. → [docs/jobs.md](../docs/jobs.md#people-sync)
- A Livestorm fetcher that returns people strips registrant join links before returning (`livestorm.payloads.strip_payload_join_links`); StormIQ never stores them. The chat fetcher asks for `include=people` only for each message's people link and drops the `included` people. A pager asks for at most `config.LIVESTORM_MAX_PAGE_SIZE` (50) per page and stops when `meta.next_page` is null. The paginated people list (`fetch_session_people`, about one call per 50 registrants) runs only in the worker (`people_sync.run_people_sync`), never in a web request, and never returns part of a list: a failed page, the deadline and a list that never reaches its last page raise.

**Models (`ai/models.py`, `ai/jobs.py`, `ai/schemas.py`, `llm_client.py`)**
- Text model ids and what each accepts live in `ai/models.py` (the catalog); each AI job's default model, effort and budget in `ai/jobs.py`. A job gets its model from `ai.jobs.resolve_model` (the classic runners call `llm_client.get_llm_model(kind)`); never hard-code a text model id elsewhere. `frontend/src/views/AdminView.vue` keeps its own list of Claude models until Admin reads it from the server, and `tests/test_model_catalog.py` checks the server accepts it. Every text job runs on Claude: never add another text provider without the owner's decision (OpenAI is for cover images and for reading Surprise me's saved take aloud, `ai/surprise_voice.py`, never for writing text).
- Read a model's parameters from its catalog row (`temperature_ok`, `effort_levels`, `max_output`…), not from the shape of its id.
- A new model setting key is checked in `ai.jobs.check_model_setting`; a saved id that is no longer offered keeps being used, with a WARNING, so classic outputs never change silently. → [docs/providers.md](../docs/providers.md#choosing-the-provider-and-models)
- Every text-model call (`llm_client.call_llm`, `generate_text`, `generate_json`) passes an `ai.usage.CallContext` (job kind, session, org, arq job id; ids only) so it is recorded in `llm_usage` once per answered call. A usage row or log line never holds a prompt, an output, a name or a key. A provider adapter returns an `llm_client.LLMResult` and never raises on an odd usage object.
- A v1 job calls a model only through `llm_client.generate_text` or `llm_client.generate_json` with its job kind, which pick the model and budget and never send `temperature`; `call_llm` is for the classic outputs. It passes a request built with `ai.request.build_request(kind, …)`, never a list of messages: the job's spec picks the layout (`JobSpec.layout`), and `ai/request.py` decides the rest from the model's catalog row (effort, adaptive thinking, the server-side fallback, the cache marker). Session data goes in the dossier (`context`) or the `payload`, never in `system` or `instructions`: those are the stable prefix, and for a dossier job the instructions are the operator's channel. Say how many calls of the run share the prefix (`shared_calls`, `call_number`), or nothing is cached. A dossier is built only with `ai/dossier.py`'s helpers (`make_dossier`, `stable_dumps`, `fixed_number`): no wall-clock time, id or randomness in it, items in id order, people by `P-` ref only. → [docs/providers.md](../docs/providers.md#request-layouts-and-caching) Every JSON step has a Pydantic schema registered with `ai.schemas.json_schema` (checked at import: closed objects, every field required, no recursion). → [docs/providers.md](../docs/providers.md#structured-outputs-and-refusals)
- A refusal (`LLMRefused`), a cut-off answer (`LLMOutputTruncated`) and an unusable one (`LLMInvalidOutput`) raise. Never catch them to save something, never retry a refusal, and never put a model's answer or refusal wording in an error or a log. A refusal's error is the same neutral message whatever its category (`llm_client.REFUSED_MESSAGE`); the category stays in `llm_usage.refusal_category`. Whether a cut-off answer is retried is `JobSpec.truncation_retry`.
- A job that runs without a user asking is marked `automatic` in `ai/jobs.py`; `llm_client` then checks the org's daily budget before each send, the truncation retry included (`ai.usage.check_org_budget`). Jobs a user starts are never held to it. The cover image call bypasses `llm_client`, so it is neither logged nor budgeted yet. → [docs/providers.md](../docs/providers.md#usage-and-the-daily-budget)

**Workspace reads**
- Get transcript insights through `api_logic._cached_transcript_insights`, once per read, and copy a shared DataFrame before modifying it.
- Don't add raw upstream payloads to the serialized workspace; add the derived table a view needs.

**Errors**
- Return `{resource, message, details}`. Log upstream URLs and bodies server-side; never return them.

**The v1 record (`record/`)**
- New code for the v1 Report goes in `record/`: pure functions over cached payloads, with no database, network or FastAPI. Classic code (`analytics/`, `api_logic`) doesn't import it, so a bug there can't break a classic read. A few exceptions import it inside the function: the record routes' loaders, `api_logic.get_session_record`, `get_session_chat_messages` and `get_session_transcript_view`; the transcription job's `worker._transcription_options`, which counts the people on stage and keeps the default speaker cap if anything in `record/` fails; and the people sync's worker side, `people_sync.run_people_sync` (field definitions, `P-` refs, the session's end). `tests/test_roster.py` checks all three (`RECORD_ENTRY_POINTS`).
- v1 data is served only by `GET /api/sessions/{id}/record` (`api_logic.get_session_record`, built by `record.assemble.assemble_record`) and, for the chat's text by evidence id, `GET /api/sessions/{id}/record/chat` (`api_logic.get_session_chat_messages`, built by `record.messages.chat_messages`, never with an author) and, for Before you share, `GET`/`PUT /api/sessions/{id}/record/figures` (`api_logic.get_session_figure_checks`, `save_session_figure_check`, built by `record.figure_checks`: answers keyed by what was said, in `session_figure_checks`) and, for the session's chapters and their show notes, `GET /api/sessions/{id}/record/chapters` (`api_logic.get_session_chapters`, from `record.understanding.chapter_list`, used only while read from the session as it is) and, for the Pulse's key moments told, `GET /api/sessions/{id}/record/moments` (`api_logic.get_session_moments`, built by `record.moments.room_moments`: what was said only when `alignment_allows(…, MINUTES)`, authors' short names only through `roster.display_people`) and, for the Report's "Who spoke up", `GET /api/sessions/{id}/record/voices` (`api_logic.get_session_voices`, built by `record.voices.chat_voices`: authors' short names only through `roster.display_people`, one message each) and, for the Transcript tab, `GET /api/sessions/{id}/record/transcript` (`api_logic.get_session_transcript_view`, built by `record.transcript_view.transcript_view`: speech on the session clock only when `alignment_allows(…, SECONDS)`, authors' short names only through `roster.display_people`) and, for the Follow-up tab's question desk, `GET`/`PUT /api/sessions/{id}/record/questions` and `GET …/record/questions.csv` (`api_logic.get_session_question_desk`, `save_session_question_reply`, `get_session_open_questions_csv`, built by `record.question_desk`: what the host saves is keyed by source and Livestorm id, in `session_question_replies`; the CSV is the one place that names askers on an internal session, through `roster.export_people`, never with an email; `PUT …/record/questions/located`, `api_logic.decide_session_located_answer`, saves the host's decision on an answer the understanding job located in the talk, read only through `record.understanding.located_answers`, which drops a result read from another dossier); never add it to `_serialize_cached_session`, and never put message text in the record. Its cache key must cover everything the block reads: when an input can change without bumping `updated_at`, add its version in `_record_input_versions` (the stored roster's `roster_version` is there). State that changes without any version (the people sync's status, a refresh that is due) is read on every request and added to a copy of the block's roster header (`people_sync.roster_live_state`), never cached. Bump `record.assemble.RECORD_VERSION` when the block or what the route adds to `record` changes, and regenerate `frontend/tests/fixtures/record-v1.json`, `record-v1-crowd.json` and `transcript-v1.json` (`.venv/bin/python tests/synthetic_session.py`). → [docs/architecture.md](../docs/architecture.md#reading-the-v1-record)
- Times come from the raw payload values (`created_at`, `responded_at`: unix seconds or ISO strings), read through `record.clock`, never from the formatted strings of the classic tables. A session without `started_at` has no clock: never fall back to `estimated_started_at`.
- Evidence ids (`C0001`, `Q001`, `A001`) come only from `record.evidence.audience_events`, and utterance ids (`U0001`) only from `record.transcript.parse_transcript`. Anything that stores one also stores the Livestorm id (or, for an utterance, its recording times). Rules: [docs/product.md §13](../docs/product.md#session-clock-v1-report).
- v1 code reads the transcript only through `record/transcript.py` (`parse_transcript`), parsed once per record build in `record/inputs.py`: it reads `result.transcription`, never the classic tables or the normalized top-level `words`. Its health is `record/transcript_health.py`, which sends counts and `U` ids, never a word, text or speaker label. Classic transcript code (`analytics/transcript.py`) stays as it is; old stored transcripts are re-based in the v1 parser only. The record reads the transcript only on a cache miss. Rules: [docs/product.md §13](../docs/product.md#transcript-health-v1-report).
- Speech reaches the session clock only through the alignment probe (`record/alignment.py`, `probe_alignment`, run once per record build in `record/inputs.py` from the parsed transcript and the events built there). `alignment_allows(alignment, resolution)` is the only code that reads its status: a finding in seconds asks for `seconds`, one in minutes for `minutes`; never branch on `status` yourself. Its thresholds are provisional constants in that module (changing one bumps `ALIGNMENT_VERSION`), and the `media_time` anchor stays off (`MEDIA_TIME_ANCHOR`) until the recording's `creation_time` is shown to mark its start. It sends our own ids and times, never a word. Rules: [docs/product.md §13](../docs/product.md#alignment-probe-v1-report).
- v1 code reads person-level data only through `record/roster.py`, loaded through `record/inputs.py`, the one place that picks the people source (`load_record_inputs`, and `count_people_on_stage` for the speaker cap); each people record is parsed by `livestorm.payloads.parse_person`. A person row keeps the email domain, never the address. A v1 prompt gets people only through `roster.prompt_view` (ref, role, job title); a page gets names only through `roster.display_people`, which fails closed. Roles never change for an internal session: read `Roster.meta.internal`. Rules: [docs/product.md §13](../docs/product.md#roster-v1-report).
- Every number the v1 Report shows is a measure in `record/measures.py` (`REGISTRY`), computed by `compute_measures` and served as `record.measures`; the SPA computes no formula. A new measure gets a `MeasureDef` (id, version, sources, gates, glossary anchor) and its section in [docs/product.md §13](../docs/product.md#measures-v1-report). Changing a measure's formula, exclusions or gates bumps its version, and any change to a version, unit, source, exclusion or gate bumps `METRICS_VERSION` and `REGISTRY_PIN` (`tests/test_measures.py` fails otherwise). An audience-only measure counts everyone on an internal session and says so (`excluded.internal`); a measure that needs authors reads `AuthorIndex` coverage and never guesses.
- A writer of a public format (the FAQ, Smart Recap, the repurposed content, the v1.1 formats such as the attendee follow-up) gets what attendees wrote or said only redacted by `api_logic._public_redactor` (`record/redaction.py`: the audience's names, emails, phone numbers and links; speakers' saved names, companies and products kept), and its output passes `_require_no_leak` before it is saved. A new public format does both; a v1.1 format goes through `api_logic.run_public_format` (`PUBLIC_FORMATS`), which also runs `record.format_briefs.check_format`. → [docs/ai-outputs.md](../docs/ai-outputs.md#public-formats-what-attendees-wrote-redacted)
- Authors are joined to people only through `record.authors.resolve_authors`, by people id. Never match an author by name, message counts or order: an author that doesn't resolve stays unresolved and its coverage says so. A chat message's people id is its `relationships.people` link; its `author_id` is a different id, never a people id. Rules: [docs/product.md §13](../docs/product.md#authors-v1-report).
