# Changelog

What has shipped, newest first. What's next is in [roadmap.md](roadmap.md).

## November 2026: all-hands fixes

- **Chat Messages counts the chat.** Session Overview's Chat Messages added up each person's `messages_count`, which Livestorm sometimes reports as 0 for everyone even when the chat has messages. It now counts the audience messages in the cached chat, as the Chat page does, and uses `messages_count` only when no chat is cached ([product.md §13](product.md#13-glossary-of-metrics-and-formulas)). The session summary sent to the AI counts the same way, an empty cached chat as 0. A person's own message count (People table, Engagement Score) still comes from `messages_count`.
- **Timelines with chat or questions alone.** Content Pace × Audience Activity and Segments With The Most Reactions were empty for a session with chat but no questions, or questions but no chat. A transcript and either source are now enough; the missing source counts 0.
- **Event session count.** The event list showed Livestorm's `sessions_count` as sent, a negative number included. A count that isn't a non-negative integer is left out of the event label and shown as "n/a".

## November 2026: v1 foundation

- **A failed job keeps only its message.** The worker now stores only a failed job's message in Redis (`queue.job_result_serializer`), the one part of it the poll reads and returns as `error`. Users see the same error text as before.
- **Registrant join links are never stored.** StormIQ doesn't need a registrant's personal join link, so the Livestorm fetchers drop `password_key` and `connection_link` before saving the session, chat and questions payloads. `scripts/strip_registrant_join_links.py` removes them from rows saved earlier, without bumping `updated_at` (`db.rewrite_base_payloads`). Nothing users see changes.
- **Livestorm page size 50.** Chat, questions and event-session calls asked for 100 items per page; the API documents 50 as the maximum. The pagers now ask for 50 and stop when `meta.next_page` is null, even after a full page.
- **Session clock.** `livestorm_app/record/` puts chat messages, questions and written answers on one time base: seconds since `started_at`, binned by minute, with the waiting room and anything after the end kept apart. Each item gets a stable evidence id (`C0001`, `Q001`, `A001`). No page uses it yet. Rules in [product.md §13](product.md#session-clock-v1-report).
- **Long recordings keep their words.** A recording over 135 minutes is transcribed in 135-minute chunks, and joining them went wrong: an empty word list hid every word, so pauses came from segments, not words; words in later chunks kept their chunk's own times; sentences and named entities after the first chunk were dropped; and every chunk reused speaker numbers from 0, so different people shared one. `gladia/transcriber._merge_chunk_results` now shifts everything onto the recording's clock, gives each chunk's speakers their own numbers, sums the billed time and records the chunks in `result.stormiq_chunks`. New long transcripts show word-level pauses, every sentence and named entity, and more speakers, since one person gets a number per chunk. Transcripts saved earlier are not rewritten. Each chunk's Gladia request is now built once, and that same request is sent; the first chunk's request is the one stored.
- **`scripts/diagnose_payload_shapes.py`** prints the shape of the payloads cached in a local database: key paths, JSON types, counts and enum-like values, never names, emails, text or URLs.
- **Roster.** `livestorm_app/record/roster.py` turns the people already cached with each session into one row per person: a role (team, guest speaker, audience), an organizer flag, a channel, a lead-time bucket, the registration answers and a `P-` ref that is the same in every parse. The roster is built in memory and limits what v1 code reads about a person: the email domain, never the address; no phone, street address, city or device data. The cached session payload is unchanged. On an internal meeting nobody is relabelled; the roster says the session is internal and counts people by role. `record/inputs.py` is the single loader of a session's record inputs. No page uses it yet. Rules in [product.md §13](product.md#roster-v1-report).
- **Chat and question authors.** The chat is now fetched with `include=people`, so each message carries its author's people id (`relationships.people`). The included people are dropped before saving: in the one real session checked, the session payload held them all, and an author missing from it reads unresolved. A message's `author_id` turned out to be a different id, so it is never read as a people id. `livestorm_app/record/authors.py` resolves each chat, question and written-answer author to a person of the roster, by people id only, and reports how much resolved per source. Chats cached earlier have no link and read "unresolved"; nobody is matched by guess. They stay that way: StormIQ doesn't fetch a cached chat again, and no page sends `forceRefresh` for it ([roadmap](roadmap.md#known-limitations)). A person's own team-flagged chat messages, or an answer they wrote, raise their role to team (a moderator registered as a participant becomes team), except on an internal session. A chat message's team flag still comes from the message, and a written answer is always team. The benchmark seed's chat has the same shape, and `scripts/diagnose_payload_shapes.py` checks chat authors by their people link. Nothing users see changes: the classic chat table leaves the link out. No page uses the authors yet. Rules in [product.md §13](product.md#authors-v1-report).
- **The record route.** `GET /api/sessions/{id}/record` serves the v1 Report's first data: the session clock, the roster's header (where the people come from, coverage, how many, and whether the session is internal) and the Pulse's audience lanes (audience chat, team chat, questions and written answers per minute, with the waiting room and after the end apart). It carries counts only, no person or message. It is a separate route, scoped like every session route and cached per session version; the classic workspace doesn't change, and a snapshot test checks it. `frontend/tests/fixtures/record-v1.json`, generated by the real route from a made-up session, is what the frontend builds against. No page uses it yet ([api.md](api.md#the-v1-record)).
- **Measures, computed live.** `livestorm_app/record/measures.py` holds every number the v1 Report will show as a measure with a stable id, a version, its sources and gates: roster coverage, audience registrants and attendees, team count, show-up rate (with Livestorm's own figure), time in the room, wrote in chat or Q&A, questions answered, time to answer, author resolution and Livestorm's counters. Each comes with its numerator and denominator, a state (`ok`, `partial`, `approximation`, `insufficient`, `unresolved`, `unavailable`), its coverage and whom it left out, so the page computes nothing. Audience-only measures say how many team members and guest speakers they left out. On an internal meeting they count everyone and say so, never 0 of 0. A chat cached before StormIQ fetched people links, or questions whose askers don't resolve, make "wrote in chat or Q&A" unresolved rather than a guess. Time in the room comes as a share and in seconds. A question's oral flag is read as the classic app reads it. The record route serves them as `record.measures` (record version 2), computed from the cached payloads with the rest of the record and never stored; `METRICS_VERSION` and a pinned registry (each measure's version, sources, exclusions and gates) keep later stored numbers comparable. No page uses them yet. Formulas in [product.md §13](product.md#measures-v1-report).
- **Grouped audience measures.** Six more measures for the v1 Report's audience section, with their numbers in rows: chat concentration (the fewest audience members who wrote half the audience chat), the room map (audience attendees by stayed or left and wrote or stayed quiet), channel quality and segment quality (per channel or select answer: registrants, show-up, who wrote among attendees, median time in the room), show-up by lead time, and replay catch-up (audience no-shows who watched the replay, and attendees who watched it again). Small channels and answers fold into one Other row and small lead-time buckets merge with a neighbour, so no small group is named or rated; a multiple select can add up to more than 100%. Rows hide their rates below their own minimum, and every row value hides when the measure's value does. Measures that need to know who wrote never guess: an old chat makes chat concentration and the room map unresolved, while channel and segment quality hide only who wrote and stay partial, since where people came from, show-up and time in the room don't depend on it. On an internal meeting they count everyone and say so. A session with no UTM, referrer or registration type, such as an internal meeting, gets an insufficient channel measure with no rows, never "direct 100%"; a form with no select field, an insufficient segment measure with no rows. Replay catch-up needs at least 10 no-shows and stays partial until the people are read at least 7 days after the session. `METRICS_VERSION` is 3 and the record version 3. A second frontend fixture, `record-v1-crowd.json`, comes from a larger made-up webinar whose grouped measures show their rows, and the benchmark's people now come from many channels and answer select fields, so `make bench` times these measures. No page uses them yet. Formulas in [product.md §13](product.md#measures-v1-report).
- **Model catalog and job registry.** `livestorm_app/ai/models.py` lists every text model StormIQ knows with what it accepts (thinking, effort, `temperature`, output limit), and `ai/jobs.py` gives each AI job its default model, effort and budget, including the v1 jobs on the Claude 5.5 models. The classic outputs now pick their model per job, with a new per-job setting `llm_model.<provider>.<kind>`; they keep the same models, settings and requests ([providers.md](providers.md#choosing-the-provider-and-models)).
- **Model usage is logged.** Every text-model call that gets an answer (`llm_client.call_llm`), a truncated, refused or retried one included, now leaves one row in a new `llm_usage` table and one `llm_usage …` line in the worker log: the job, session, org and arq job id, the model asked for and the one that answered, why it stopped, the token counts (cache reads and writes too), an estimated cost from the catalog's prices, the time taken and the request id. Never a prompt, an output or a key. Each provider's answer becomes one `LLMResult` (`llm_client`); `call_llm` still returns only the text, so the classic outputs, prompts and models don't change. If the row can't be saved, the job logs it at ERROR and still saves its output, a deliberate exception to "writes raise". Rows stay when their session is deleted ([data-model.md](data-model.md#llm_usage)). The cover image call isn't logged yet ([roadmap](roadmap.md#5-models)).
- **A daily AI budget per org, for automatic text jobs.** `ORG_DAILY_LLM_BUDGET_USD` stops one org's automatic text jobs for the rest of the UTC day once its estimated spend reaches it. The worker checks it before each send, the truncation retry included. No text job runs automatically yet, so it limits nothing today, and jobs a user starts are never held to it. An automatic job on a session with no org never runs, and with a budget set it never calls a model that has no price. The cover image job, which the worker chains after a Professional recap, isn't held to it ([providers.md](providers.md#usage-and-the-daily-budget)).
- **Admin refuses unknown model ids.** Saving a model setting checks it against the catalog and returns a clear message with the choices; any non-empty text used to be saved. A model saved earlier that Admin would now refuse keeps working, with a warning in the worker log. An older model setting that names the other provider's model is skipped, so the job uses its default instead of failing.
- **Speaker cap.** Gladia was always told to look for up to 20 speakers, which invites speakers that don't exist. A new transcript now asks for at most the people on stage plus two, between 3 and 20. People on stage are the session's organizers and guest speakers, counted in the same people as the v1 roster: today, the people cached with the session (`record/inputs.count_people_on_stage`). When nobody is marked on stage, as on an internal meeting where nobody is marked as an organizer, the cap stays at 20: a cap of 3 would be too low for a room where many people talk. New transcripts may show fewer speakers; transcripts saved earlier are not touched ([product.md §13](product.md#transcript-level)).
- **Gladia job metadata and provenance.** Each Gladia job now carries ids only: the session, the recording and its size, an environment tag (`render` or `local`), the chunk and its offset, and a fingerprint of the settings sent. This prepares re-attaching to a Gladia job after a timeout, for the right recording only; re-attaching isn't built yet ([roadmap](roadmap.md#known-limitations)). The stored transcript records how it was made in a `stormiq` block: the settings fingerprint, the speaker cap and the count it came from, each Gladia job with the metadata sent, and the recording file's duration and `creation_time` ([data-model.md](data-model.md#session_cache)).
- **Transcript parser and transcript health.** `livestorm_app/record/transcript.py` reads a stored Gladia transcript for the v1 Report: utterances get stable ids (`U0001`, by start) and each word its utterance's id. It reads the words inside the utterances, or `result.transcription.words` when Gladia sent a non-empty list, so an empty list never hides them. Long transcripts saved before the merge fix kept their later parts' words on the part's own clock; the parser moves them onto their utterances in memory, for those transcripts only, and nothing is written back. `record/transcript_health.py` says how far a transcript can be trusted: word-level confidence and the share of unclear words, speech coverage counted once when people talk over each other, substantial speakers against the people on stage, speech in which no speaker was found, the split risk, the language against the event's, the stretches of unclear words, a state (`ok`, `degraded`, `poor`, `unavailable`) with its reasons, and whether pace and speaker shares may be shown. Thresholds are provisional. The record route serves it as `record.transcriptHealth` (record version 4) and as the measure `m.transcript_health` (metrics version 4); it carries counts and utterance ids only, never a word or a speaker label. The record reads the transcript only when it builds its block, never on a cache hit. Classic transcripts, tables and charts don't change. No page uses it yet ([product.md §13](product.md#transcript-health-v1-report)).
- **A refusal says so.** When the model declines a session, a classic output now fails with "The model declined this session. Nothing was saved." instead of "The model returned an empty …". Nothing is saved, and the refusal is not retried: content repurposing stops after one paid call instead of three. Its usage row is kept, with the outcome `refused` and Anthropic's refusal category when it gives one; the message never names the category. Any partial text the model wrote before declining is dropped. Prompts, models and formats of the classic outputs don't change ([ai-outputs.md](ai-outputs.md#saving-rules)).
- **Structured outputs for the v1 jobs.** `llm_client.generate_json(kind, schema, …)` sends a JSON step's schema to the provider (Anthropic `output_config.format`, OpenAI strict `response_format`) and validates the answer against the full Pydantic model; `generate_text(kind, …)` is the same for text. Both take the model and budget from the job, send no `temperature`, and check the stop in order: refusal, then the token limit (retried only when the job's spec says so, `JobSpec.truncation_retry`; the classic outputs keep their one retry), then the schema. An answer that fails its schema raises `LLMInvalidOutput` and is recorded as `invalid_output`. Schemas are Pydantic models registered in `ai/schemas.py`, turned at import into the strict subset both providers accept. Nothing calls them yet ([providers.md](providers.md#structured-outputs-and-refusals)).
- **The alignment probe.** `livestorm_app/record/alignment.py` works out where the recording sits on the session clock, so speech can be read against the chat. It looks for moments where the two meet: a link the host announces and posts, a call to the chat ("tell us in the chat", "bonjour à tous") followed by a burst of audience messages, and a question or message read aloud (found through a token index of the transcript, accents folded, English and French cues). Each gives a range for the offset; a message or an utterance feeds one anchor at most, and team chat is never read aloud, so one moment can't confirm itself. The range most of them agree on, checked against the recording's and the session's lengths and again on each half of the recording, gives a status: `verified` (the agreed offset, ±15 s at most), `assumed` (offset 0), `misaligned` or `unavailable`. One gate, `alignment_allows`, decides what may use it: findings in seconds need verified, findings in minutes verified or assumed. Every threshold is provisional, to tune on sessions checked by ear; the recording file's `creation_time` isn't used until it is shown to mark the start. The record route sends it as `meta.clock.alignment` (ids and times only, never a word), adds the speech lanes (speaking seconds and words per minute) to the Pulse when findings in minutes are allowed and says why otherwise, and serves the measure `m.clock_alignment`, ok only when the clock is verified (record version 5, metrics version 5). `scripts/probe_alignment_study.py` prints each session's result and an ear-check worksheet of recording times, never text. The synthetic webinar behind the frontend fixtures now verifies an offset of about +19 s. No page uses it yet ([product.md §13](product.md#alignment-probe-v1-report)).
- **People storage and the paginated people list.** Four new tables hold a session's people for the v1 Report: `session_rosters` (one header per session: version, source, coverage, Livestorm's count, field definitions), `session_people` (one row per person, as `parse_person` reads it: the email domain, never the address; no join link), `org_people_attributes` (the workspace's registration field labels) and `livestorm_sync_jobs` (the people sync's rows, which hold the user's connection id only until the worker claims them). A roster is replaced whole in one transaction (`db.replace_session_roster`), so a failure keeps the previous one, and deleting a session deletes its people. Reads are scoped through the session's org. `livestorm/client.py` gains the paginated people list (`fetch_session_people`: 50 per page, each person once, join links stripped, complete only when the people match Livestorm's `record_count`, a deadline, the monthly rate-limit header; a failed page, the deadline or a list that never reaches its last page raises, so it never returns part of a list) and the people attributes (`fetch_people_attributes`; a refusal reads `forbidden`). Nothing calls them or writes the tables yet; the people sync job comes next ([data-model.md](data-model.md#stored-people), [security.md](security.md#stored-people), [providers.md](providers.md#livestorm-people)).
- **`scripts/diagnose_people_cap.py`** counts what Livestorm's people endpoints return for local sessions (whether `include=people` is capped, whether the lists and counters include the team, whether the people attributes answer and how answers match them, whether the monthly rate-limit headers come back), with `LS_API_KEY` from the environment. It prints integers and yes/no only.

## November 2026: internal sessions

- **Internal sessions count everyone.** Audience-only chat metrics left nothing on an internal meeting, such as an all-hands, where everyone is a team member: Messages, Unique Chatters, Avg Msg Length, Top Contributors, Activity Over Time, the cross-source timeline, Most Engaged People and the chat stats sent to the AI dropped to zero, with "Excludes your team (n)". When team members are more than half of the attendees ([product.md §13](product.md#13-glossary-of-metrics-and-formulas)), nothing is left out, the cards say "Internal session: everyone counts" and the AI is told the session is internal. Public sessions are unchanged.

In the classic sidebar it keeps its on-dark colours whatever the system theme. The Livestorm icon PNGs and the `/brand-assets` route that served them are gone.

## November 2026: fixes before the rebuild

- **Audience-only chat metrics.** Chat from the team and guest speakers no longer counts as audience activity: Messages, Unique Chatters, Avg Msg Length, Top Contributors, Activity Over Time, the cross-source timeline, Session Overview's Chat Messages and the chat stats sent to the AI count the audience only, with "Excludes your team (n)" on the cards. The Chat tab still lists every message, with a "From" column.
- **Session Overview.** Most Engaged People leaves out team members and guest speakers; Attendance By Country plots attendees, not registrants.
- **Cross-source timeline.** The last chat message and the last question were always dropped (they fell in a 100% bucket past the end).
- **Oral answers.** The questions field is read with the API's spelling (`response_orally`, falling back to `responded_orally`), and a question answered orally counts as answered, in the app and in what the AI sees.
- **Card language.** The session-card API returns the event's language; it was read from the session, which has none. Cards don't show it yet.
- **Content Repurposing on an empty transcript** fails the job instead of saving "Transcript is empty." four times. Bundles saved that way earlier are treated as missing, so they can be generated again.
- **PDFs** carry the StormIQ mark instead of the Livestorm logo, a "not an official Livestorm product" footer (in French for French exports), real bold text and no literal `---` lines. Exports are named `stormiq-…` instead of `livestorm-…`.
- **Models.** `temperature` is sent only to the Claude models that accept it, so Opus 4.7 and 4.8 work when chosen; Admin offers Opus 4.8 in place of 4.7. gpt-image-1, shut down by OpenAI, is gone from Admin, and a saved gpt-image-1 setting is sent as gpt-image-2.
- **Surprise Me!** shows a CSS spotlight instead of an image.

## November 2026: structure

- **#11 Module split.** `app.py` (776 lines) became the entry point plus one router per area in `livestorm_app/routes/`; `services.py` (3,000 lines) became `livestorm/` (API client), `analytics/`, `ai/` and `pdf.py`. ## November 2026: hardening

Security, data-integrity, reliability and performance fixes from the November 2026 review, merged as pull requests #1 to #7.

- **#7 Frontend logic.** Session-scoped async work in the store: switching session aborts the old session's requests and drops late results, and AI jobs always target the session on screen. Loading flags owned by the call that set them. Polls ride out transient failures. Central 401 handling that keeps shared links working. `markRaw` workspace. Lazy-loaded routes (entry bundle 272 → 135 KB). Encoded path params. Formula-safe CSV export and stable table row keys. AI job polls return only the outputs. The first frontend tests (Vitest).
- **#6 Backend performance.** A 2-hour session opens in about 0.1 s instead of 4.5 s: an O(mentions × sentences) entity lookup replaced, and transcript insights built once per read and cached per session version. The workspace response is about 3.5× smaller (raw payloads dropped, raw transcript moved to `transcript.json`). A Postgres connection pool and one long-lived Redis pool. Polls and the card list read only the columns they need. System settings cached for a minute. Immutable caching for hashed assets. A per-request timing log and a local benchmark.
- **#5 Job reliability and cost.** Deterministic arq job ids replace the Redis in-flight marker, and a failed job can be retried at once. Reading a session never starts a paid cover image, and the post-recap cover trigger works again. One active transcription per session, with dead queue jobs detected instead of blocking for an hour. `/fetch` no longer transcribes inside the web request. Retries with backoff and timeouts on every LLM, Livestorm and Gladia call. Per-job timeouts, a two-transcription concurrency cap, and cancellation handling. No credentials in job arguments. Language and tone validated before any paid job. AI job polls no longer trust a client-supplied job id.
- **#4 Base image pins** for the October 2026 Node.js security release: exact `node` and `python` base images and `frontend/.nvmrc`.
- **#3 Data integrity.** Atomic per-entry bundle writes (`merge_cached_bundle_entry`). `account_key_hash` insert-only. Database write failures raise instead of being swallowed. Empty, truncated or incomplete AI output fails the job instead of being saved. A transcription heartbeat for the stuck-job sweeper.
- **#2 Safety net.** A local Postgres in compose and `.env.example`. Hashed dependency locks (uv). Ruff and ESLint, with the issues they found fixed. Real-Postgres and pure-function tests. CI. Slimmer non-root images with health checks.
- **#1 Access control.** Fail-closed org scoping on every session route (`livestorm_app/auth.py`), a path-traversal fix in the SPA route, local-dev mode behind `STORMIQ_LOCAL_DEV` instead of the Host header, Secure cookies, CORS removed, handshake expiry enforced, upstream error details no longer returned, and the access-control route matrix.

## Earlier

- `session_cache.organization_id`: teammates in one Livestorm org share cached results; other orgs can't read them.

### Background jobs

- Redis and an arq worker (`Dockerfile.worker`), stage-floor progress in Redis, and the stuck-job sweeper.
- Transcription moved from a web-process thread to an arq job; restarts no longer kill transcriptions in progress.
- The four AI flows moved to arq jobs with poll routes, so long deep analyses no longer hit the proxy timeout. The frontend polls them and shows an `AiJobProgress` bar (English and French stage labels), including for transcription.
- Server-side dedupe of AI jobs, so double-clicks don't enqueue twice.
